# 0.4.3 investigation

## Custom application links — issue #4

Source: [Allow all apps to Direct Link](https://github.com/HeklaLab/gatearr/issues/4).

The report contains a reproducible bug and a separate feature request.

**Confirmed bug:** Applications & API filtered the custom-link editor by both `access_service` and the display label. A custom link called Sonarr, Tracearr, Radarr, Bazarr, Tdarr, Emby, Jellyfin or Seerr remained stored in `menu_items` but was omitted from its editor. Repeated creation therefore accumulated rows visible to the application catalog without edit/delete controls. A reinstall is unnecessary: the records can be exposed again.

**Local correction:** use explicit integration association rather than a display name to classify editor rows. Independent custom links retain their `menu:<id>` catalog identity, even with the same name. Legacy native-card aliases keep their existing destinations. Tests cover all eight names, five existing Sonarr entries, editing one entry, deleting another without affecting the remaining rows, and legacy published-card compatibility.

**Separate requested enhancement:** the author clarified that "widgets" meant application cards. They want a direct-link option for native applications such as Tracearr and Sonarr, to build an administrator-only section of application links. Restoring the custom-link editor does not implement that new setting. Direct URLs need a browser-reachable address and must not expose stored API credentials or silently change native access permissions. Implemented locally: each placed card stores its opening mode and optional browser destination. A complete enabled integration offers direct/embedded choices; an unconfigured tool offers direct only with a required public destination. Direct bookmarks do not enable the protected proxy.

### Issue #6 — independent destinations for two Emby cards

Source: [Multiple Widgets cannot act differently](https://github.com/HeklaLab/gatearr/issues/6).

**Reproduced in the browser:** two separate published application blocks each contained `access:emby`. Both initially linked to `/access/emby`. Changing only the first card's "When clicked" setting to Direct link changed both published links to `/services/emby/open`, without publishing the portal. Changing it back restored both guide links.

**Confirmed cause:** the builder submits only the service key to `/admin/design/home/application/emby/behavior`. That endpoint writes the shared `AccessService.entry_mode`; there is no card-specific destination override.

**Implemented correction:** store opening behavior and an optional direct destination per application occurrence in each portal block, freezing the existing service behavior during migration for old layouts. Keep connection credentials and library data shared, while destinations and audiences remain independent. Stage these choices in the portal draft and apply them on publication; changing a draft card must not change the live portal immediately. Preserve existing application permissions.

### Issue #5 — Emby direct link uses Gatearr's port

Source: [Emby Link Broken](https://github.com/HeklaLab/gatearr/issues/5).

**Not reproduced with the tested explicit public addresses.** Six isolated endpoint tests checked the final HTTP 303 Location for same-host and different-host addresses, HTTP port 8096, HTTPS port 8920, a reverse-proxy subpath, `/web`, and `/web/index.html`. Each retained the configured Emby port and expected path. Native identity verification was stubbed in these endpoint tests. The full demo browser redirect was blocked by HTTP 502 because the simulator's user-profile endpoint accepts the API key but rejects its own user-session token; this is a limitation of the simulator and does not establish a production Emby failure.

The relative `/services/emby/open` link intentionally uses Gatearr's host and port before the server redirects to Emby. Seeing that initial link is not evidence that the final destination uses the wrong port.

**Proposed investigation/correction boundary:** obtain the reporter's configured public browser address, the affected card destination and final redirect Location without tokens. Check legacy custom-link overrides and stale saved addresses as well as native direct links. Use one canonical, browser-reachable public media address; preserve its scheme, hostname, explicit port and base path, with no fallback to Gatearr's origin. The exact production cause remains unconfirmed, so no speculative fix is marked complete.

## Image block and uploads — issue #8, diagnosis only

The user confirmed that adding an Image block produces a large Emby logo and that their replacement upload does not take effect. No application code was changed during this investigation.

**Confirmed default-image defect:** `studio.js` initializes ordinary image blocks with `boot.widgets.icons.widget_media`, the Emby/Jellyfin icon. The isolated browser test rendered this default Emby image at 512 × 512 pixels.

**Confirmed hidden dimension restriction:** Portal builder and the email editor upload through `/admin/assets`, which uses the icon sanitizer. PNG dimensions must each be at most 1024 pixels even though the builder's error only mentions PNG/SVG and 5 MB. A valid 1920 × 1080 PNG weighing only a few KB returned HTTP 400 with the dimension restriction. A 320 × 180 PNG returned HTTP 200, replaced the preview and persisted in the draft in a browser test. A valid small SVG returned HTTP 200 in a direct endpoint test. Uploads are therefore not universally broken; the HD-image failure is independently reproduced. The reporter's exact file has not been tested.

**Why the old image remains:** a rejected upload never calls the callback that updates the block URL. Subsequent saves retain the original Emby asset. The UI discards the server's detailed rejection reason and shows a generic message. No successful-HD-upload persistence claim is made.

**Local correction after approval:** reuse the existing logo crop/resize editor for both Portal builder and the email editor. Large PNG, SVG, JPEG and WebP source images are adjusted in the browser and converted to a bounded PNG before reaching the existing protected upload endpoint. Page-image sources may be up to 40 MB and 40 megapixels before conversion; the existing 5 MB/1024-pixel server constraints remain in place for the processed output. Existing logo-input behavior is retained. Empty portal images now show a neutral placeholder in the editor and are omitted from public pages until configured.

**Browser validation:** an original PNG over 5 MB is accepted by the adjustment dialog, resized to at most 1024 pixels per side, uploaded successfully and retained in the portal draft after reload. Cancelling another selection preserves the saved image and sends no upload. A 1920 × 1080 image is resized, uploaded, saved into an email template and present after reopening it. These checks used an isolated database, without sending email or changing the main demo's saved content.

## Tdarr — hash-route address reproduces the reported failure

The supplied address ended in `/#`. Gatearr appended resource paths to that string, producing URLs such as `http://tdarr.private:8265/#/static/css/main.css`. The resource path became a browser fragment, which is not sent in an HTTP request. Tdarr therefore received `/` and returned its SPA index instead of CSS/JavaScript. The returned HTML contained the normal Tdarr index and Gatearr's injected bridge, matching the screenshot's MIME errors.

**Reproduced:** the same saved `/#` form makes a CSS request receive HTML before the fix. Regression tests also cover `/#/` and `/#/home`.

**Local correction:** strip the browser fragment when saving/testing Tdarr addresses and when consuming existing saved addresses in HTTP/WebSocket proxy routing. Old configurations benefit without a database reset. Keep query validation, native authentication, MIME checks and per-request Gatearr permissions.

The corrected browser test uses an isolated native Tdarr 3.01.00 server and an isolated Gatearr database, configured with the reported hash-address form. This cannot by itself establish that the user's production deployment has no additional proxy or authentication issue. As an immediate configuration workaround, use the private WebUI root address without `/#`.

## Validation

491 automated tests passed, one optional export skipped, with one existing dependency warning. Before correction, the native-name editor test and the saved-hash CSS test both failed in the reported manner. After correction, an isolated native Tdarr 3.01.00 instance rendered its login screen through Gatearr with the saved `/#` form, no browser script errors and no incomplete-loading notice. CSS and runtime configuration returned HTTP 200 with `text/css` and `application/javascript`. The unauthenticated native verify-token endpoint returned its expected HTTP 401. This is a loading validation, not a new authenticated transcoding/job-management test.

The production configuration can be corrected immediately by replacing the browser URL with the WebUI root address, for example `http://tdarr:8265`, and saving it. Production confirmation remains necessary.

## Current per-card implementation and compatibility

The diagnosis-only sections above record the initial reproduction. The local 0.4.3 changes now store `application_behaviors` by stable application identity inside each placed application block. The old global mutation endpoint returns 410. Migration 0027 freezes existing opening modes and legacy explicit destinations into draft and published snapshots, preserving content and invalidating stale editor revisions. Connection credentials and guide contents remain shared; the placed card owns its opening choice.

Complete integration configuration is determined by an enabled API URL and API key (Tdarr needs no API key), with the interface switch respected for Tracearr/Tdarr. A direct URL is a browser address, never inferred from a private API endpoint. Admins can display external bookmarks for unconfigured tools; this does not grant a protected frame or API access. Existing embedded cards become dormant when their integration is unavailable, rather than silently changing destination. Ordinary users still require explicit tool permission; Tracearr and Tdarr remain administrator-only native tools.

Custom application names never choose a native identity. Same-named custom links can be edited, deleted and assigned their own guides independently. Existing legacy name-based destinations are preserved only in already-saved snapshots, not applied to new native cards.

Browser checks on an isolated demo copy exercised direct/embedded choices for all five tools, two independent Emby destinations, draft/live isolation, publish/reload and builder widths 320, 390, 640, 900 and 1440. These checks validate Gatearr routing and settings; they do not prove the reporter’s private deployment or every external application session.

Final local regression run: **520 passed, one optional export skipped, one existing dependency deprecation warning**. Browser verification also covered the unconfigured-tool path (direct-only selector, public URL entry, publication and HTTP 403 for the protected frame), image resize/cancel/persistence in the portal and email editor, and installed history with five release series and no unpublished 0.4.3 entry. The main demo was backed up before applying migration 0027; its saved data was reused. No release or GitHub issue was published or closed.

## Follow-up: browser handoff and editor spacing

The main demo’s saved user-token profile lookup returned HTTP 403: its simulator accepted the API key on `/Users/{id}` but omitted the already-existing own-user session authorization. The simulator now accepts a native session for its own profile only; another user’s profile and the user list remain forbidden. This corrects demo behavior, not a newly proven cause of issue #5 in the reporter’s deployment.

`/services/emby/open` remains the protected automatic-login step. Its browser destination comes from the public interface URL, not the private Application URL. If a normal user has no valid automatic-login session or native verification is unavailable, open the configured public WebUI without a token. Explicit identity mismatch, disabled users and changed private connections remain rejected. Active administrator assistance does not acquire a fallback identity or reuse the administrator’s token. If the assisted source session disappears and assistance ends, only an unauthenticated native sign-in URL may be returned. Tests check those boundaries and explicit port/base-path preservation.

Guide-builder titles now use plain text selection with a separate action row; palette forms provide an explicit vertical gap before the background-gradient switch, and advanced application-address settings have space before the API-key field. A browser matrix covered six theme variants at 320, 390, 900 and 1440 pixels; the reusable layout check now also asserts the palette-to-gradient gap.
