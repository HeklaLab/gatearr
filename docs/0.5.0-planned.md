## #13 — Combined audience selection requested on 28 October 2026

Planning only: do not implement or change the current demo yet. Before application development, prepare a separate functional demonstration of the selection buttons and their dependent states for review.

- Use one combined audience selector for ordinary blocks and widgets, listing **Everyone**, **Administrators**, and every configured user group. Remove **Members**; actual groups replace that option.
- Allow multiple groups and **Administrators** together. Matching is inclusive: membership in any selected group OR Gatearr administrator status when Administrators is selected makes the user eligible. Do not require both administrator status and group membership.
- **Everyone** means every user, including users with no assigned group. Turning it on selects all group buttons and Administrators. Turning it off clears the selection.
- While Everyone is selected, deselecting a group or Administrators turns Everyone off and retains the other selected buttons, switching to that explicit audience. All buttons remain usable; no contradictory Everyone-plus-exclusions state.
- Selecting all listed groups manually must not silently include ungrouped users; only Everyone represents unrestricted audience eligibility.
- No selected audience means nobody matches. Administrator status does not bypass explicit group targeting when Administrators and Everyone are off; an administrator can still match through a selected group.
- Demonstrate at least: Everyone on/off; one or several groups; Administrators only; Administrators plus a group; deselecting a group from Everyone; empty selection; and a user with no group. Show both the button states and which sample users can see the block.
- Apply the same audience meaning in the editor, preview and published rendering, including ordinary blocks and existing widgets. Existing application permissions remain separate from block visibility.

The detailed button transitions above are to be reviewed in that demonstration before implementation. No functional mockup or application code has been created for this request.

## #12 — Investigation completed in unmodified 0.4.4 (28 October 2026)

The complete causal chain of the locally reproduced failure was established before the implementation described below. This supersedes the initial limited diagnostic above; it does not claim access to the reporter's database.

### Root cause and evidence

1. **Two separate publication levels are presented as the same operation.** `app/visual_howto.py:choices` creates new guides with only a draft and `published=None`. Its journey Publish action updates the choice tree, not its referenced guides. `article` publishes an individual guide separately. Saving a guide, even with valid filled steps, leaves it unpublished.
2. **One unpublished dependency blocks the entire journey.** `app/access.py:validate` checks every referenced guide when the journey is published. It checks the entire tree, including other submenus, not just the menu currently visible in the editor. Browser links and plain groups have no such publication dependency.
3. **Existing guide edits can appear not to publish without returning an error.** If a guide already has a published snapshot, saving its edited draft and publishing the journey succeeds, but its old public instructions remain unchanged. Only publishing that guide replaces its public snapshot.
4. **The interface hides this dependency.** `howto_editor` supplies a `published` flag for each guide, and `new-guide` returns it too, but `app/static/visual-howto.js` does not use that flag to label the guide choices. The same generic Publish label appears in the guide and journey editors. It also does not distinguish an unchanged published guide from one with unpublished draft edits.
5. **The actionable error is discarded by the client.** The server returns HTTP 400 and a paragraph explaining that a published guide must be selected. `request()` in `app/static/visual-howto.js` searches the returned page with `main .lead,main p:last-child`. In `app/templates/error.html`, the message paragraph has no `lead` class and is followed by a link, so neither selector matches. Browser inspection confirmed that the error is visible in `main p` while that exact client selector matches zero elements. The user therefore sees only “Unable to save. Check your settings and try again.” The error also fails to name the blocking guide/path.
6. **Why Emby initially looks different:** `app/default_journeys.py:seed` installs six Emby guides with their draft and published snapshots already populated. `seed_seerr` creates an empty journey with no prepublished guides. New Seerr/custom-app guides therefore expose the hidden dependency immediately; this is shared builder behavior, not Seerr-specific publication logic.

### Validation completed

Four isolated diagnostic cases passed: the full lifecycle independently for Emby, Seerr and a custom Discord app, plus fresh-install default-state verification. Each lifecycle checked all of the following:

- Browser choice plus an empty Phone submenu publishes successfully.
- A newly created guide saves, but blocks journey publication before it is published.
- Filling and saving that guide is insufficient; publication still returns the unpublished-guide error.
- Publishing the guide then the journey succeeds, and the public page contains its instructions.
- Editing/saving the guide and publishing only the journey retains the previous public instructions.
- Publishing the guide makes the new instructions visible.
- An unpublished guide in another submenu blocks the entire tree.

An additional browser walkthrough reproduced the failure, published a valid step in the guide editor, returned to the journey and published successfully without changing its connection settings. Error-template inspection independently confirmed the broken client selector. Test databases and browser modifications were isolated from the main demo; no real SMTP messages were sent.

### Implementation scope ready for 0.4.5

- Keep draft/public isolation and the guard against exposing unpublished guide content; do not silently publish guide drafts as a side effect of journey publication.
- Distinguish **Publish guide** from **Publish journey** and explain the dependency in the editor.
- Display guide states explicitly: unpublished draft, published, or published with unpublished changes. Compare draft and published snapshots; a published boolean alone is insufficient.
- Before publishing a journey, identify every blocking guide by name and submenu path and provide its edit destination. Do not hide blockers in another branch behind a generic failure.
- Return/render an actionable error consistently instead of extracting it with the broken CSS selector. Include guide identifiers/paths for this validation case, while retaining normal authorization and input validation.
- Preserve the existing successful behavior for links, valid submenus and already-published guides, and cover both first publication and later guide edits with regression checks based on the matrix above.

The reporter's exact stored tree was not supplied. The shared defects and their implementation scope are fully diagnosed above; attributing a particular blocker in that private tree would require seeing that tree, rather than inventing its contents.
